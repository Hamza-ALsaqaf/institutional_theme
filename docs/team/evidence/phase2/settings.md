## Validation (all on the server; no message offers "save anyway")

- Default preset must be allowed (the custom preset needs `allow_custom`). A preset that is not shipped is not a valid default.
- Custom preset: both colours required and six-digit hex; the preset is generated by `midad.custom_preset` and rejected when any pair fails, with one list item per failing pair: label and token name (`<bdi dir="ltr"><code>`), mode, ratio and required ratio (each in `<bdi dir="ltr">`), and which colour to adjust. `custom_audit` is stored language-neutral (`passed / total · lowest ratio`).
- Uploaded pairing: all four files required. Every set font file must be a public `/files/` file whose first four bytes are `wOF2`, `00 01 00 00` or `true` (`fonts.file_kind`); a private file, an external URL, a missing file or another format is rejected.
- Emblem and favicon must be public (an addition to ADR 0005, which lists only fonts: a private emblem breaks the login page).
- Idle warning between 1 and 30 minutes, checked only while the warning is enabled.
- `environment` is filled in `onload` from `site_config.ins_environment` and cleared in `validate`, so it is never stored.

`mandatory_depends_on` is client-side only in Frappe, so the same requirements are enforced in `validate`.

## Finding: a custom preset cannot currently fail

`custom_preset` keeps only hue and chroma (chroma multiplier at most 1) and takes lightness from the approved curves. I tried 26 extreme inputs (pure primaries, white, black, grey) and chroma multipliers up to 8: none produced a failing pair. The rejection path is therefore defence in depth. It is tested against a copy of the model in which the "Text on primary action" minimum is raised to 30 (every failing pair named, `<ul>`, bdi markup, nothing stored). ADR 0005's test "a pale custom primary is rejected" cannot be written as stated: a pale primary passes, and the test instead asserts that it passes.

## Identity write-through

- Only changed fields are written (previous document compared with the saved one); `frappe.has_permission(..., "write", throw=True)` first.
- Website Settings via `frappe.db.set_single_value` (dict) and the cache clearing of its `on_update`; Navbar Settings via `get_single(...).save()`.
- First write of a key stores the target's current value in global `ins_identity_prior`; every written value is in `ins_identity_written` (JSON, `frappe.db.set_global`). Clearing a settings field puts the prior value back.
- `restore()` returns each target that still holds the value this app wrote to its prior value, leaves a target an administrator changed, clears both globals, is idempotent. `delete_attachments()` deletes the File rows attached to the doctype.
- NOT wired yet: `before_uninstall` belongs to `install.py` (Phase 3). That task must call `identity_sync.restore()` and `identity_sync.delete_attachments()` (in that order). Until then uninstalling does not restore identity. The functions are tested directly. `hooks.py` enables nothing.
- NOT done (Phase 3 by instruction): `site_files.ensure()` on save. `on_update` only runs the write-through; add the guarded import there.
